本書は、AI活用研修全4回の知識を**現場で即使える形**に凝縮した秘伝書です。

## この研修が存在する理由

### この研修の目的は「AIを知ること」ではない

AIについて詳しくなること、でも、やる気を出すこと、でもない。

この研修の唯一の目的は——

> **「AIに"使われる側"ではなく、AIを"使い倒す側"になるための、最も合理的な"武器"を手に入れること」**

---

### 5年後、エンジニアは2種類に分かれる

好むと好まざるとに関わらず、エンジニアの仕事は激変する。

「仕事がなくなる」という単純な脅しではない。事実は——

**クソ面倒な仕事と単純な仕事が、AIによって消滅する。**

これはエンジニアにとって、究極的には「暇になる」ことを意味する。
問題は、その「暇」になった時に、エンジニアが2種類にハッキリ分かれることだ。

---

#### タイプA：「合理的安定」を選ぶエンジニア

週5日・40時間かかっていた仕事を、AIという"外部頭脳"を使って週2日・10時間で終わらせる。

成果は誰よりも出しながら、ストレスも・責任も・面倒な人間関係も、AIに肩代わりさせる。

**AIのメカニズムを知り尽くした「使い手」だけが到達できる、圧倒的なコストパフォーマンスの未来。**

#### タイプB：「人間的価値」にフォーカスするエンジニア

コードを書く、バグを潰す、仕様書を読む——そういう「作業」は全部AIに任せる。

そして、自分が本当にやりたかったこと——クライアントと直接話して「本当に作りたいもの」を考えるとか、人と人を繋ぐサービスを企画するとか。

**AIが「作業」を代行してくれるからこそ、「人と接する」という理想の働き方を選ぶ選択肢が生まれる。**

---

### そして、3つ目の道

もちろん、3つ目の道——**「AIに言われたことだけをやる"道具"」**になる未来もある。

この研修は、皆さんをその道に行かせないためにある。

そして、タイプAの未来を選ぶか、タイプBの未来を選ぶか、その**「選択権」**を皆さん自身が握るためにある。

---

### この本に書いてあることの意味

プロンプト・RAG・ローカルLLM……これらは単なる「知識」ではない。

- タイプAの未来（効率化）を選ぶための **『武器』**
- タイプBの未来（選択肢）を選ぶための **『チケット』**

これは「勉強」じゃない。**未来のゲームのルールを先読みするためのハッキングだ。**

## 2. 第1回の秘伝

### テーマ：プロンプトとコンテクストの本質

#### 黄金法則：AIは「コンテクストの奴隷」である

AIは天才ではない。**渡された情報の範囲内でしか答えられない確率機械**だ。
「良い答えが出ない」の9割は、プロンプトの問題ではなく**コンテクストの問題**。

#### メタプロンプト：一度作れば一生使える

```
あなたは[役割]の専門家です。
以下の制約に従って回答してください。

【制約】
- 回答は[文字数/形式]で出力すること
- [禁止事項]は絶対に行わないこと
- 不明な場合は「わかりません」と答えること

【コンテクスト】
{{ここに状況説明を入れる}}

【質問】
{{ここにユーザーの質問を入れる}}
```

#### 第1回の3つの秘伝

| 秘伝 | 内容 | 現場での使い方 |
|------|------|---------------|
| **役割を与える** | 「あなたは〇〇のエキスパートです」 | 「ベテランVB.NETエンジニア」など具体的に |
| **制約を先に書く** | 「〜してはならない」をプロンプト前半に | 「再起動してはならない」「DEL_FLGに触るな」など |
| **出力形式を指定する** | 「JSON形式で出力してください」 | プログラムで受け取るならJSON必須 |

## 3. 第2回の秘伝

### テーマ：AIをコーディングパートナーにする

#### コメント駆動開発（CDD）の作法

コードを書く前に、**コメントで仕様を書く**。それをAIに読ませる。

```vb
' 【仕様】顧客IDを受け取り、過去3ヶ月の売上合計を返す
' 【入力】customerId As Integer
' 【出力】totalSales As Decimal（円単位）
' 【エラー】顧客が存在しない場合は -1 を返す
' 【注意】T_ORDER テーブルを参照。DEL_FLG は配送済みフラグ（削除フラグではない）
Function GetSalesTotal(customerId As Integer) As Decimal
    ' GitHub Copilotがここを実装してくれる
End Function
```

**ポイント：「注意」欄に社内固有の罠を書く。** AIは一般的な知識しか持たないので、ローカルルールは必ずコメントで伝える。

#### 第2回の3つの秘伝

| 秘伝 | 内容 | アンチパターン |
|------|------|---------------|
| **仕様はコメントで書く** | コードより先にコメントを書く | 「いい感じに作って」は死 |
| **型と形式を指定する** | `Double` / `ISO8601` / `3桁ゼロ埋め` | 「9割くらいの精度」は死 |
| **例外を設計する** | エラー時の振る舞いを決める | 「とりあえずスキップ」は死 |

## 4. 第3回の秘伝

### テーマ：データを「AIの飯」に変える技術

#### 大原則：「ゴミを食わせるとゴミが出る」

AIに「なんかヤバそうなやつを教えて」と聞いても正確に答えられない。
AIには**判断させるな、計算させるな。答えを探させろ。**

```
【悪い設計】
  生のExcelやPDFをそのままAIに渡す
    → AIが自力で計算・判断しようとして間違える

【良い設計】
  Python等で前処理 → 確定値をJSONで渡す → AIは「解釈」だけする
    → 計算済みの数値 + 確定したフラグ を渡す
```

#### データエンジニアリング 4つの変換作業

```
[Step 1] 数値の定量化
  「9割くらい」→ 0.94
  「左上のあたり」→ {"x": 120, "y": 85, "width": 45, "height": 30}
  「1月20日 朝9時くらい」→ "2025-01-20T09:15:32Z"

[Step 2] 計算の事前実施
  「前回メンテから14日経過したか？」→ プログラムで計算して "maintenance_alert": true を付与
  「不良率3%を超えているか？」→ プログラムで計算して "defect_rate_percent": 4.5 を付与

[Step 3] ノイズの除去
  「インフルエンザにより欠勤」→ "status": "Absent" に統一
  個人情報・不要な備考欄は削除

[Step 4] メタデータの付与
  {"target_line": "A", "category": "trouble", "date": "2025-01-20"}
  → これによりAIへの検索フィルタリングが可能になる
```

#### チャンキングの鉄則

| チャンクの切り方 | 良否 | 理由 |
|----------------|------|------|
| 固定文字数（500文字）で切る | ❌ 悪い | 「Line A」と「100個/h」が別チャンクになる |
| Markdown見出し（H2）単位で切る | ✅ 良い | 意味のまとまりが保たれる |
| テーブル単位で切る | ✅ 良い | 数値とラベルの関係が壊れない |

#### 第3回の3つの秘伝

| 秘伝 | 一言 |
|------|------|
| **確定ロジックはコードで書く** | 「3%超えたか？」をAIに判断させるな。Pythonで判断してから渡せ |
| **メタデータでフィルタリングする** | ラインAの話をしているときにラインBの情報が混入しないよう制御する |
| **リランクで順位を補正する** | 「不良多発」という文脈なら「精密モード」を1位にする |

## 5. 第4回の秘伝

### テーマ：社外秘をAIに食わせる禁断のレシピ

#### 「線を抜く」の意味

```
【クラウドAI（ChatGPT等）】
  あなたのPC → インターネット → OpenAIのサーバー → 回答が戻る
                ↑
          ここで社外秘が漏れる

【ローカルLLM（Llama 3.1等）】
  あなたのPC内で完結。インターネット不要。
  LM Studio（プレイヤー）+ Llamaモデル（CD）= 完全オフラインAI
```

#### 「秘伝のタレ」RAGの実装パターン

```
secret_manual.md  ←「社外秘の宝」
      ↓
Semantic Kernelで読み込む
      ↓
プロンプトテンプレートに埋め込む

【プロンプトテンプレート】
あなたは社内システムのベテランエンジニアです。
以下の【社内マニュアル】のみに基づいて回答してください。
知識にない場合は「わかりません」と答えてください。

【社内マニュアル】
{{$manual}}

【ユーザーの質問】
{{$input}}
```

#### Semantic Kernelを使う理由

この研修ではVB.NETとPythonの両方を使ってきた。
言語が違っても、AIとの繋ぎ方を統一できるのがSemantic Kernelの最大の強みだ。

```
【Semantic Kernelがない場合】
  VB.NET側   → OpenAI API（VB.NETで実装）
  Python側   → OpenAI API（Pythonで実装）
  ← 言語ごとにAIとの繋ぎ方を別々に実装・管理

【Semantic Kernelを使う場合】
  VB.NET側  ┐
             ├→ Semantic Kernel → OpenAI API
  Python側  ┘                  → Llama API（ここだけ変える）
  ← VB.NETでもPythonでも「同じ文法」でAIを扱える。
    接続先の切り替えも設定1行で完了。
```

Semantic Kernelは**「VB.NETとPythonの間に立つ通訳」**でもある。
言語の壁を越えて同じ設計思想でAI機能を作れるから、チームで分担しやすい。

#### ローカルLLMの現実的な弱点

| 弱点 | 規模感 | 対策 |
|------|--------|------|
| 速度が遅い | GPT-4の5〜10倍遅い | RAGでヒット精度を上げて質問回数を減らす |
| 精度が落ちる | GPT-4の1/10サイズ | Few-shotで例を見せる。出力形式を厳密に指定する |
| 日本語が怪しい | モデル依存 | より日本語が得意なモデルを探す（CommandR+等） |
| プログラムが崩れる | JSON出力が特に失敗しやすい | プログラム側で再試行ロジックを実装する |

#### 第4回の3つの秘伝

| 秘伝 | 内容 |
|------|------|
| **人格を固定する** | 「ベテランエンジニアとして」「マニュアルのみに基づいて」で幻覚を防ぐ |
| **接続先を抽象化する** | Semantic Kernel経由にすることで、将来の「脳の載せ替え」を容易にする |
| **プログラム側で防御する** | AIの誤回答をエラーハンドリングで受け止め、再試行する仕組みを作る |

## 6. 現場AI構築 鉄板パターン集

### パターンA：「新人の代わり」型
**用途：** ベテランしか知らない知識を新人でも引き出せるようにする

```
[構成]
秘伝のタレ（社外秘マニュアル）.md
    ↓ RAG
ローカルLLM（Llama 3.1）
    ↓
VB.NETアプリ or Webチャット
    ↓
新人エンジニアが質問する

[実例]
Q: 「顧客サーバーAで502エラーが出た。再起動していい？」
A: 「再起動は絶対にするな！DefOneAgentをタスクキルしろ！」
```

### パターンB：「コード仕様書化」型
**用途：** 担当者が辞めたレガシーコードの仕様を自動生成する

```
[構成]
レガシーコード（.vb / .php）
    ↓ ファイル1つずつ読み込む
ローカルLLM
    ↓
日本語の仕様説明 + テストコード を生成
    ↓
Markdown / .vb ファイルとして保存

[実例]
Input:  OrderManager.dll の中の謎の関数
Output: 「この関数は受注データを更新します。DEL_FLGは配送済みフラグであり...」
```

### パターンC：「エラーログ解析」型
**用途：** 過去のトラブル対応ログをAIに学習させて、再発時に即座に解決策を提示する

```
[構成]
過去3年分のトラブル対応ログ.csv
    ↓ RAG（チャンク化・ベクトル化）
クラウドLLM（GPT-4）※公開情報なのでクラウドOK
    ↓
社内チャットボット or メール自動返信

[実例]
Input:  「今朝からLine_Bでエラー502が頻発。最終メンテから16日経過。」
Output: 「類似事例2件発見。2024-03-15と同一パターン。対処法：①DefOneAgentをタスクキル...」
```

### パターンD：「日報AI処理」型
**用途：** 毎日届くExcel日報をAIが自動で集計・異常検知する

```
[構成]
Excelファイル（毎日17時に届く）
    ↓ Python で前処理（数値化・フラグ付け）
クラウドLLM（GPT-4）
    ↓
「今日のサマリー + 要注意事項 + 明日の推奨アクション」
    ↓
Teamsへ自動投稿

[実例]
Output: 「本日のLine_C不良率4.5%（閾値3%超過）。精密検査モードへの切り替えを推奨。
         類似事例によると、研磨工程の刃物交換が原因の可能性が高い。」
```

## 7. 失敗学：これをやると死ぬ10の罠

### 罠1：「いい感じに」で指示する
```
❌ 悪い例: 「この日報をいい感じに要約してください」
✅ 良い例: 「この日報を以下のJSON形式で要約してください。
            {"summary": "50文字以内", "alerts": ["異常項目のリスト"], "urgency": "high/mid/low"}」
```

### 罠2：DEL_FLGを削除フラグだと思う（現場固有の罠）
```
❌ 死のクエリ: WHERE DEL_FLG = 1 → 配送済みデータがヒット → 請求ミス！
✅ 正解:      WHERE MEMO LIKE '%DELETE%' → 削除済みデータが正確にヒット

→ 教訓: 「名前が示す意味」と「実際の仕様」は別物。社内固有ルールはAIに教えない限りAIは知らない。
```

### 罠3：社外秘をクラウドAIに投げる
```
❌ 危険: 「ChatGPTにソースコードを丸ごとペーストして解析させる」
✅ 安全: ローカルLLM（Llama 3.1）+ LM Studioでオフライン処理
```

### 罠4：AIを再起動ボタンだと思う（顧客サーバーAの教訓）
```
❌ 死の判断: 「502エラーが出た。とりあえず再起動！」
              → DBの整合性チェックが走り、朝まで復旧しなくなる大事故

✅ 正解: DefOneAgent.exe をタスクキル → C:\App\Unlocker.bat を実行
→ 教訓: AIもネット情報で「再起動が一般的な対処法」と答える。社内ルールは必ず「秘伝のタレ」に書け。
```

### 罠5：固定文字数でチャンクを切る
```
❌ 悪い例: 「500文字ごとに切る」→ 「Line A ｜ Rank A ｜ 能力: [改行]100個/h」が分断される
✅ 良い例: Markdown見出し（##）やテーブル単位で切る
```

### 罠6：ハルシネーションを信用する
```
AIが提案した関数: JsonSerializer.DeserializeWithAutoMapping()
実際の存在:       存在しない！（命名規則が正しくてもAPIが実在するとは限らない）

→ 対策: 出力したコードは必ずドキュメントとIDEで確認する
```

### 罠7：AIに計算させる
```
❌ 悪い例: 「前回メンテから何日経ったか計算して」をAIに聞く
✅ 良い例: Pythonで計算して "days_since_maintenance": 16 をJSONに入れ、AIに渡す

→ 法則: 確定的なロジックはコードで。あいまいな判断のみAIに任せる。
```

### 罠8：精度を追いすぎてリリースできない
```
❌ 100%の精度を目指して永遠にリリースできない
✅ 「70%の精度でも、現状（0%）より価値がある」場合は出す

→ ただし: 安全に関わる判断（機械停止・人員配置）には必ず人間のレビューを挟む
```

### 罠9：プロンプトだけで解決しようとする
```
❌ 悪い例: ひたすらプロンプトを改良して精度を上げようとする
✅ 良い例: データの前処理（チャンキング・メタデータ）を先に改善する
→ 回答品質の9割はデータエンジニアリングで決まる。プロンプトは最後の1割。
```

### 罠10：全部AIにやらせようとする
```
❌ 過信: 「AIが全部やってくれる」
✅ 現実: AIは「道具」。道具を使うエンジニアの設計力が全てを決める。

→ Semantic Kernelの言葉で言えば:
  Semantic Function（AIの文系スキル）× Native Function（あなたのコード）
  この掛け算の設計こそが、エンジニアの仕事。
```

## 8. AIを選ぶ技術：クラウドかローカルか

```
データに「社外秘」「個人情報」「ソースコード」が含まれる？
          │
         Yes → ローカルLLM（Llama 3.1 + LM Studio）一択
          │
         No
          │
          ↓
精度が最優先か？
          │
         Yes → クラウドLLM（GPT-4 / Claude 3.5 / Gemini 1.5）
          │
         No（コスト優先）
          │
          ↓
ローカルLLM（Llama 3.1）でも十分な場合が多い
```

### モデル選択チートシート

| 用途 | 推奨モデル | 理由 |
|------|-----------|------|
| 社外秘コード解析 | Llama 3.1 8B（ローカル） | セキュア・無料 |
| 高精度な文章要約 | GPT-4o（クラウド） | 精度最高峰 |
| 大量文書のRAG | Command R+（クラウド/ローカル） | 長文コンテクスト対応 |
| 日本語特化 | Gemma 2 JPN（ローカル） | 日本語の精度が高い |
| 将来のファインチューニング | Llama 3.1（ローカル） | 商用ファインチューニング可 |

## 9. 最終チェックリスト

### AIを現場に出す前の10項目

```
データ設計
□ 数値は全て定量化されているか（「高め」→ 0.94）
□ 日時はISO 8601形式か（「朝9時くらい」→ "2025-01-20T09:15:32Z"）
□ 計算が必要なロジックはプログラムで処理済みか（AIに計算させていないか）
□ チャンクは意味のまとまりで切られているか（固定文字数ではないか）
□ メタデータのタグは付いているか（いつ、どのライン、どのカテゴリ）

セキュリティ
□ 社外秘データがクラウドに送られていないか
□ ローカルLLMを使う場合、ネットワーク遮断で動作確認したか

プロンプト設計
□ AIの役割（人格）が明確に定義されているか
□ 「わからない場合はわかりません」という指示があるか
□ 出力形式（JSONなど）が厳密に指定されているか

システム設計
□ AIが誤回答した場合のエラーハンドリングがあるか
□ 接続先（クラウド/ローカル）の切り替えが容易な設計か（Semantic Kernel推奨）
□ 安全に関わる判断には人間のレビューが入る設計か

評価
□ 「攻めるAI」で悪意ある質問に対する回答を確認したか
□ ハルシネーション（もっともらしい嘘）が出た場合の対処を設計したか
```
