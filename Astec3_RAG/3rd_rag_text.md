### 1. RAGの基礎と必要性（30分）

ここでは「なぜRAGが必要か」を、身近なエンタメの例を使って直感的に理解させます。

**① 導入：LLMの知ったかぶり（ハルシネーション）**

- **事例:**    
    - **幻のAPI提案:** `JsonSerializer.DeserializeWithAutoMapping()` のように、命名規則には合っているが実在しない関数を平然と提案してくる。
        
    - **レガシーと最新の混同:** 2020年の古い規約を、2025年の最新版として解説する（AIには時間の前後関係の判断が難しいため）。
    
- **なぜ起きる？:** LLMは「学習時点までの知識」しか持たず、確率で言葉を繋いでいるだけだから。
    
- 解決策: 先に「教科書（外部データ）」を渡して、「これを見ながら答えて」と指示する＝これがRAG。RAGに「辞書」としての役割だけでなく、「検証用フィルタ」としての役割を持たせる設計が必要です。
    

**② 仕組み：言葉を「数字（ベクトル）」にする**

- **ベクトルデータベースとは:** コンピュータは言葉の意味を理解できない。だから「数字の列（ベクトル）」に変換する。
    
- **イメージ:** 「猫」「犬」「車」の例。
    
    - 「猫」と「犬」は数値的に近い（フワフワ度、動物度）。
        
    - 「車」は遠い。
	        
    - 質問文のベクトルに近いデータをデータベースから引っ張ってくる（類似性検索）。

**「時間軸」と「優先順位」の設計：**

- **静的知識（マニュアル）：** 普遍的なルール。
- **動的知識（工場の稼働ログ）：** 「今」起きていること。
- **過去事例（トラブル履歴）：** 似たケースをどう解決したか。
    
- これらを同じフォルダに放り込むのではなく、**「メタデータ」**を使ってAIに「これはいつの、何のデータか」をタグ付けして教える技術を学びます。



実践してみると「思ったような答えが返ってこない」ことがあります。その原因の9割は、AIの頭の良さではなく、**データの渡し方（Engineering）**にあります。

#### ① 「ゴミを食わせるとゴミが出る」 (Chunking & Filtering)

ただPDFを読み込ませるだけでは動きません。データを「AIが消化しやすい一口サイズ」に切る技術が必要です。

- **チャンキング (Chunking)**
    
    - **悪い例**: 文字数（例:500文字）だけで機械的に切ると、今回配ったマニュアルの「標準能力表」が真っ二つになります。ヘッダー（Line A）と値（100個/時）が別々のチャンクになり、AIは数値の意味を理解できなくなります。
    - **ワークでの改善策**: 
        
        20_manual_knowledge.md のように、**
        
        ```
        H2
        ```
        
        見出し**や**Markdownのテーブル単位**で「意味のまとまり」として分割します。これを「セマンティック・チャンキング」と呼びます。
- **ノイズとフィルタリング (Metadata)**
    
    - **失敗例**: 「エラー」という単語だけで検索すると、今日はLine Aの話をしているのに、無関係な「Line Bのエラー909（包装機ジャム）」までヒットしてしまいます（"Fate"問題）。
    - **ワークでの改善策**: インデックス化する際に、各チャンクに 
        
        ```
        target_line: "A"
        ```
        
         や 
        
        ```
        category: "trouble"
        ```
        
         というタグ（メタデータ）を埋め込みます。検索時にこのタグでフィルタリングすることで、無関係な情報を物理的に遮断します。

#### ② 検索結果の並び順 (Re-ranking)

- **リランクの必然性**
    - **今回のシナリオ**: 昨日の日報に「Line C不良多発」とありました。この状況でマニュアルを検索すると、「通常モード(200個/h)」と「精密検査モード(80個/h)」の両方がヒットする可能性があります。
    - **Lost in the Middle**: もし「通常モード」が上位に来てしまうと、AIはそちらを使って計算し、「なんだ、余裕で間に合うじゃん」と誤った人員配置を出してしまいます。
    - **解決策**: 検索エンジンから返ってきた上位10件に対し、リランカー（再順位付けAI）を使って、「**日報の文脈（不良多発）**に照らして、本当に重要なのはどっち？」と再評価させます。「精密検査」の順位を強制的に1位に引き上げることで、AIの計算ミスを防ぎます。

#### ③ RAGの評価と改善 (Evaluation)

- **グラウンディング (Grounding)**
    - AIが出した答えが「もっともらしい嘘」でないかチェックする仕組みです。
    - 例えば、AIが「鈴木(Rank C)と佐藤(Rank B)を組ませる」と回答した場合、その根拠として引用されたマニュアルの「ペア制約」セクションを自動で読みに行き、本当にその組み合わせが許可されているかをプログラムで事後検証します。これを実装して初めて「客先に納品できるシステム」になります。

## 1. マニュアルの構造化 (`20_manual_knowledge.md`)

  

工場長の書いた `raw_manual.txt` は文章が長く、条件が散らばっていました。これをどう切るかがポイントです。

  

* **Point 1: テーブルによる正規化**

* **Raw**: 「ラインA（組立）の場合、熟練者(A)は100個/h...」

* **Reasoning**: 文章だと「ラインAのBランク」を探すのにコストがかかります。

* **Solution**: `| ラインID | 工程 | ランク | 能力 |` のマトリクス表に変換しました。これによりAIは座標で数値を特定できます。

  

* **Point 2: 条件式のコード化**

* **Raw**: 「前回メンテから14日経過すると効率が一律80%に落ちるそうです」

* **Reasoning**: "そうです" という文末はノイズです。「14日」という閾値を明確にする必要があります。

* **Solution**: `条件: (今日の日付) - (最終メンテナンス日) > 14日` というプログラミング言語に近い記法で定義し、曖昧さを排除しました。

  

* **Point 3: エラー対応のルール化**

* **Raw**: 「エラー502（ジャム）が出た翌日は...稼働率90%」

* **Solution**: 検索キーとして `Error 502` を明記し、アクションを `稼働率係数 0.9` に定量化しました。

## 2. 日報のJSON化 (`21_production_log_yesterday.json`)

  

手書き風の `raw_daily_report.txt` から、計算に必要な数値を抽出します。

  

* **Key Challenge: 隠れたアラートの顕在化**

* **Raw**: 備考欄に「Line Aのメンテを最後にやってから今日で11日目になる」と記述あり。

* **Engineering**:

* 単にテキストをコピーするのではなく、`"days_since_maintenance": 16` (1/5〜1/21) を計算してフィールド化しました。

* マニュアルの「14日ルール」に引っかかるかどうかを、JSON生成時点で判定し、`"maintenance_alert": true` フラグを立てています。

* **ここまでやるのが「データエンジニアリング」です。** AIに計算させるのではなく、データ側で計算しておくのです。

  

* **Line Cの不良率計算**

* **Raw**: 「生産数: 2000, 不良: 90」

* **Engineering**: 割り算を実行し、`"defect_rate_percent": 4.5` を算出。マニュアルの「3%ルール」を超えていることを明確にします。

## 結論：なぜここまで加工するのか？

  

「AIなら元のテキストでも読めるのでは？」と思うかもしれません。

しかし、**「計算（14日経過したか？）」や「判断（3%を超えたか？）」を推論時にやらせると、AIは間違えます。**

確定的なロジックはデータ前処理（Pythonコード等）で済ませ、AIには「その結果どうすべきか」という **高度な判断のみ** に集中させる。

これが実用的なRAGシステムの基本設計思想です。

## 具体的な実践的RAGプロンプトの作り方
「AIに作らせ、別の視点のAIで評価・検証・テストする」

| **役割**    | **担当**  | **具体的アクション**                               |
| --------- | ------- | ------------------------------------------ |
| **作るAI**  | 準備用LLM  | 言葉を「数値」に変換し、データベースに保存する。                   |
| **繋ぐAI**  | 実行用LLM  | データベースの情報を読み比べて、矛盾を解消して人間が実行可能なアクションに変換する。 |
| **測るAI**  | 評価用LLM  | 検索された知識が、現場の課題解決に「本当に役立つか」を採点する。           |
| **攻めるAI** | テスト用LLM | 膨大な「意地悪な質問」を投げ続け、システムの弱点を洗い出す。             |

> 
> **【コンテキスト】**
>
