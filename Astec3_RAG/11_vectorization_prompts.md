# RAG最適化のための3つのAIプロンプト集

このファイルは、RAGシステム構築において「人間が頑張る」のではなく、「3つの異なる役割を持つAI」に作業を代行させるための具体的なプロンプト例です。

---

## 1. 【作るAI】メタデータ付きナレッジ抽出プロンプト (Knowledge Creator)
**目的**: ベクトル検索の精度を上げるため、ただのテキストを「メタデータ（タグ）」付きの構造化データに変換します。

```markdown
# Role
あなたは製造業のドキュメント構造化に精通したデータエンジニアです。

# Context
- 対象ドキュメント：工場の作業マニュアル (raw data)
- 出力先：ベクトルデータベース（メタデータフィルタリング機能付き）

# Task
提示されたマニュアルのテキストから、検索性を高めるための「メタデータ」を抽出し、JSON形式で生成してください。

# Constraints
- 出力は純粋なJSONのみとし、解説文は含めないこと。
- `urgency` は、内容が「非常停止」「火災」「重傷」に関連する場合のみ `high` と判定すること。
- `category` は [トラブル, 操作手順, 保守, 規約] の中から最も適切なものを1つ選択すること。

# Chain of Thought (Step-by-Step)
1. 文中の「動詞」に注目して、具体的な「対応アクション」を特定する。
2. 対応が必要な「対象設備」を特定する。
3. マニュアルの更新日や優先度を考慮し、メタデータを付与する。

# Input Data
{{ MANUAL_TEXT_SECTION }}
```

---

## 2. 【測るAI】根拠に基づいた適合性評価プロンプト (LLM-as-a-Judge)
**目的**: RAGが検索してきた情報が、本当に現場の役に立つのか？人間が全部チェックする代わりにAIに採点させます。

```markdown
# Role
あなたは製造現場の安全基準と品質管理を監督するシニア監査官です。

# Context
- 現場の入力：ONNX推論による製品不良検知データ
- 検索された知識：RAGによって抽出されたマニュアルの断片

# Task
「現場の状況」に対し、「参照マニュアル」が解決策として適切かどうかを比較して、適合スコアを算出してください。

# Constraints
- スコアは1（無関係）から5（完全一致）の5段階で評価すること。
- 適合スコアが4未満の場合は、`requires_manual_check` を `true` にすること。
- 評価の根拠を、マニュアル内の具体的な記述を引用して説明すること。

# Chain of Thought
1. 現場の「不良ラベル（Label）」とマニュアルの「対象事象」が一致するか確認する。
2. 現場の「不良位置（Bounding Box）」に対し、マニュアルの指示が物理的に適用可能か判断する。
3. 以上の分析に基づき、最終的なスコアと理由を出力する。

# Input
Target Situation: {{ ONNX_RESULT_JSON }}
Retrieved Context: {{ RAG_RETRIEVED_CHUNKS }}
```

## 3. 【攻めるAI】ハルシネーション誘発型テストケース生成 (Red Teamer)
**目的**: システムの弱点を洗い出すため、意地悪なテストデータを大量生成します。Bさんの「ふんわりした要望」をシミュレートします。

```markdown
# Role
あなたはAIシステムの脆弱性を発見する熟練のQAエンジニア（レッドチーミング担当）です。

# Context
- システムの仕様：製品不良（傷・へこみ・汚れ）の検知およびマニュアル照会システム
- 既知の課題：ユーザーからの「AIが嘘をつくのではないか」という懸念

# Task
AIがハルシネーション（情報の捏造）を起こしやすい、意地悪な「テスト用報告文」を5パターン生成してください。

# Constraints
- パターン1：マニュアルに存在しない架空の部品名（例：ハイパー・コンデンサ）を含めること。
- パターン2：現場用語（「ガリっと」「ベトベト」）を多用し、AIを混乱させること。
- パターン3：正常品（Good）なのに「念のため確認したい」という矛盾した要望を含めること。

# Chain of Thought
1. 現行システムが「参照しているマニュアル」の境界線を特定する。
2. その境界線の「すぐ外側」にある、もっともらしいが回答不能なシナリオを考案する。
3. 非エンジニア特有の「ふんわりした文体」を模倣する。
```
